## أبسط نظام إضافات تم بناؤه

ماذا لو كان تعليم وكيل ذكاء اصطناعي مهارة جديدة بسيط مثل كتابة مستند؟ مو ملف بايثون. مو ملف YAML. مو حاوية Docker. فقط ملف ماركداون يوصف ماذا تسوي المهارة وكيف تنفذها.

هكذا تشتغل مهارات وولف فيش. حط مجلد فيه ملف `SKILL.md`، والوكيل يتعلم شيء جديد فوراً.

## كيف تشتغل

المهارة هي مجلد يحتوي على ملف `SKILL.md` واحد. الملف يوصف المهارة بلغة عادية — ماذا تسوي، متى تستخدمها، وكيف تنفذها. الوكيل يقرأ هذا الملف ويدمجها في حلقة التفكير حقته.

هيكل بسيط:

```
my-skill/
  SKILL.md
```

و `SKILL.md` ممكن يكون كذا:

```markdown
# نشر للإنتاج

## متى تستخدم
لما المستخدم يطلب نشر أو دفع للإنتاج أو شحن آخر التغييرات.

## الخطوات
1. شغّل مجموعة الاختبارات وتأكد كلها تنجح
2. ابنِ حزمة الإنتاج
3. ادفع للفرع الرئيسي
4. شغّل خط النشر
5. تأكد إن النشر سليم
```

هذا كل شيء. بدون SDK. بدون تسجيل API. بدون خطوة بناء.

## لماذا الماركداون يشتغل

مهارات الماركداون تشتغل بسبب طريقة معالجة بنية الدماغ في وولف فيش للمعلومات. طبقة التفكير ما تحتاج كود منظم لتفهم النية — تحتاج وصف واضح للأهداف والخطوات والقيود.

المزايا كبيرة:

- **صفر منحنى تعلم**: إذا تقدر تكتب README، تقدر تبني مهارة
- **قابل للتحكم بالإصدارات**: المهارات ملفات — حطها في git
- **قابل للمشاركة**: أرسل لشخص مجلد وعنده مهارة جديدة
- **قابل للتعديل**: حدّث مهارة بتعديل ملف نصي — بدون إعادة بناء
- **قابل للفحص**: اقرأ بالضبط ماذا الوكيل بيسوي قبل ما يسويه

## أمثلة من الواقع

المستخدمين بنوا مهارات لكل شيء من ترحيل قواعد البيانات إلى كتابة الإيميلات إلى توفير البنية التحتية:

- **سير عمل Git**: يوحّد رسائل الكوميت وتسمية الفروع
- **مراجعة الكود**: يحلل الفروقات حسب إرشادات الفريق
- **خط البيانات**: ينسّق مهام ETL عبر مصادر بيانات متعددة
- **التوثيق**: ينتج تلقائياً وثائق API من تغييرات الكود

## نظام المهارات البيئي

لأن المهارات مجرد مجلدات ماركداون، مشاركتها سهلة جداً. انسخ مجلد من جهاز لآخر. استنسخ ريبو git. حمّل ملف zip. المهارة تشتغل فوراً — بدون تثبيت، بدون تبعيات، بدون إعدادات.

هذه البساطة مقصودة. أفضل نظام إضافات هو اللي يختفي.
